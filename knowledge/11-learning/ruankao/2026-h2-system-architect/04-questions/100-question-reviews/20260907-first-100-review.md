## 三、详细知识总结

### 1. 软件开发方法与过程模型

#### 1.1 结构化方法

🔴 **结构化方法**强调**自顶向下、逐步分解、逐步求精、功能分解**。先从整体系统出发，再将复杂问题逐层拆成更小的模块或功能。

#### 1.2 原型模型

🔴 **原型模型**适用于**需求不明确、用户难以一次性说清需求**的场景。先快速做出可演示原型，让用户反馈，再持续迭代修改。

核心不是“最终产品做得快”，而是：

> 用原型帮助用户和开发人员澄清需求。

#### 1.3 瀑布模型

🔴 **瀑布模型**适合**需求稳定、阶段边界清晰、变更较少**的项目。

典型顺序：

```text
需求 → 设计 → 编码 → 测试 → 维护
```

#### 1.4 螺旋模型

🔴 **螺旋模型最强关键词：风险分析。**

适用于：

- 大型项目
- 复杂项目
- 高风险项目
- 需要多轮迭代和风险控制的项目

Q3 错误提醒：题干出现“高风险 + 每轮风险分析”，优先锁定**螺旋模型**。

#### 1.5 V 模型

🔴 **V模型强调开发阶段与测试阶段的对应关系。**

重点记忆：

> **需求分析 ↔ 验收测试**

高层需求对应高层测试；越靠近代码，测试粒度越细。

### 2. 软件测试

#### 2.1 测试阶段

| 测试类型 | 主要关注点 | 题干关键词 |
|---|---|---|
| 🔴单元测试 | 最小可测试单元内部逻辑 | 函数、类、模块内部 |
| 🔴集成测试 | 模块连接后的接口与协作 | 单独正常，连接后出错 |
| 🔴回归测试 | 修改后确认原有功能未被破坏 | 修改、修复后重新验证旧功能 |
| 🔴链接测试 | Web 链接正确性、孤立页面 | 链接错误、目标不存在、孤儿页面 |

Q23 错误提醒：系统修改后重新验证购物车、订单、支付等旧功能是否仍正常，是**回归测试**，不是 AB 测试。

#### 2.2 黑盒与白盒

- 🔴 **黑盒测试**：不关心内部代码，只看输入输出是否符合要求。
- 🔴 **白盒测试**：关注内部逻辑、控制流、分支、路径。

口诀：

> 黑盒看外面，白盒看里面。

#### 2.3 黑盒常见方法

| 技术 | 核心思路 |
|---|---|
| 🔴等价类划分 | 把输入划成若干有效/无效等价类，每类取代表值 |
| 🔴边界值分析 | 错误容易出现在边界附近，取边界及边界前后值 |
| 🔴判定表 | 多个条件组合对应不同动作 |
| 🔴错误猜测法 | 基于经验和历史缺陷猜测容易出错的位置 |
| AB测试 | A/B 两个版本随机分组比较点击率、转化率等 |

### 3. 软件架构风格

| 五大架构风格 | 典型子风格 |
|---|---|
| 🔴数据流风格 | 批处理、管道-过滤器 |
| 🔴调用/返回风格 | 主程序/子程序、面向对象、分层架构 |
| 🔴独立构件风格 | 进程通信、事件驱动 |
| 🔴虚拟机风格 | 解释器、规则系统 |
| 🔴以数据为中心 | 数据库系统、黑板系统、超文本系统 |

批处理 vs 管道-过滤器：

> **批处理：一批一批过阶段。**  
> **管道-过滤器：一段一段流过去。**

### 4. MVC、MVP、MVVM

| 模式 | 核心中间角色 | 职责 |
|---|---|---|
| MVC | 🔴Controller | Model 负责数据/业务；View 负责显示；Controller 负责交互控制 |
| MVP | 🔴Presenter | View 与 Model 更彻底分离，交互集中在 Presenter |
| MVVM | 🔴ViewModel | 连接 View 与 Model，负责状态转换、数据绑定等 |

Q40 错误提醒：**接收用户动作并控制流程 → Controller**，不是 View。

### 5. SOA 与微服务

#### 5.1 SOA 三角色三动作

| 角色 | 职责 | 动作 |
|---|---|---|
| 服务提供者 | 真正提供业务服务 | 🔴发布服务 |
| 服务消费者 | 查找并使用服务 | 🔴发现、🔴绑定 |
| 服务代理 | 保存服务描述、帮助查找 | 注册/目录信息 |

口诀：

> **提供者发布；消费者发现；找到以后绑定。**

Q50 错误提醒：提供者把服务登记到注册中心是**发布**，消费者去查询才是**发现**。

#### 5.2 微服务 vs SOA

| 比较项 | 微服务 | SOA |
|---|---|---|
| 服务粒度 | 更细 | 相对更大 |
| 集成方式 | HTTP/REST/JSON | ESB/WS/SOAP |
| 总线 | 强调无集中式总线 | 常见 ESB |
| 开发部署 | 独立开发、测试、部署 | 依赖相对复杂 |

口诀：

> 微服务：**小、轻、独立**。  
> SOA：**大、总线、集中**。

### 6. 云计算与边缘计算

这是今天的**第一优先级薄弱区域**。

#### 6.1 SaaS / PaaS / IaaS

| 模式 | 提供内容 | 最短判断 |
|---|---|---|
| 🔴IaaS | 虚拟服务器、存储、网络等基础设施 | 给资源 |
| 🔴PaaS | 运行环境、中间件、平台能力 | 给平台 |
| 🔴SaaS | 已经完成的标准应用软件 | 给软件 |

最短口诀：

> **I 给资源，P 给平台，S 给软件。**

Q59/Q62 错误提醒：如果操作系统、中间件和运行环境已经由平台准备好，开发人员主要部署自己的应用，属于**PaaS**。

#### 6.2 云计算体系结构五层

| 层次 | 快速判断 |
|---|---|
| 用户访问层 | 怎么访问 |
| 🔴应用层 | 直接使用什么业务应用 |
| 🔴平台层 | 怎么构建/运行自己的应用 |
| 资源层 | 底层虚拟化资源 |
| 管理层 | 统一管理、安全、监控、计量 |

Q67/Q68 错误提醒：

> **直接提供财务、CRM 等业务软件 → 应用层。**  
> **支持用户构建自己的应用 → 平台层。**

#### 6.3 边缘计算

🔴 **边缘计算**强调在**靠近数据源的一侧**完成网络、计算、存储和应用处理。

核心结论：

> **计算处理职能的本地化。**

Q70 错误提醒：在线财务软件属于 SaaS 场景；工厂现场边缘设备先处理传感器数据，再上传必要数据，才是边缘计算。

### 7. DSSA

🔴 **DSSA（特定领域软件架构）**面向某个特定应用领域中的一组应用，抽取共同特征，形成可复用领域架构。

关键词：

> **特定领域 + 一组应用 + 共性抽象**

- 垂直域：一个较小领域/行业内部，**专、深**。
- 水平域：多个行业都可通用，**广、横跨行业**。

### 8. ABSD

🔴 **ABSD：Architecture-Based Software Design，基于架构的软件设计。**

软件架构是主要驱动力。

三个基础必须记牢：

> **分功能、选风格、用模板。**

即：

1. 🔴功能分解
2. 🔴选择架构风格
3. 🔴软件模板的使用

Q75 错误提醒：软件模板本身属于 ABSD；边界值分析属于测试，因此“不包括”的是边界值分析。

### 9. 架构质量属性

| 质量属性 | 最短理解 | 高频词 |
|---|---|---|
| 🔴性能 | 快不快 | 响应时间、吞吐量、每秒请求数 |
| 🔴可用性 | 坏了还能不能用 | 故障、恢复、宕机、备用服务器 |
| 🔴安全性 | 该不该让你访问 | 认证、授权、加密、未授权访问 |
| 🔴可修改性 | 好不好改 | 修改成本、影响范围 |
| 🔴易用性 | 好不好学/用 | 界面友好、学习时间、便利性 |
| 🔴可测试性 | Bug 好不好测出来 | 调试接口、观察、定位缺陷 |

注意：

> 出现数字不一定就是性能。  
> “故障后 30 秒恢复”属于**可用性**；“2 秒响应”才偏向**性能**。

### 10. 质量属性场景六要素

| 要素 | 回答的问题 | 示例 |
|---|---|---|
| 🔴刺激源 | 谁发起？ | 用户、设备、外部系统 |
| 🔴刺激 | 发生什么？ | 查询请求、服务器故障 |
| 🔴环境 | 当时什么状态？ | 高峰期、正常运行、维护状态 |
| 🔴制品 | 作用到哪里？ | 系统、模块、组件、服务 |
| 🔴响应 | 系统做什么？ | 返回结果、切换备用节点 |
| 🔴响应度量 | 做到什么程度？ | 2秒内、30秒内、99.99% |

口诀：

> **谁 → 发生什么 → 当时什么状态 → 作用到哪里 → 系统做什么 → 做到什么程度。**

Q86 错误提醒：刺激发生时系统所处的运行条件或状态叫**环境**；刺激发生后系统采取的动作才叫**响应**。

### 11. SAAM 与 ATAM

#### 11.1 SAAM

🔴 **SAAM 最初主要分析可修改性。**

Q90 错误原因就是忽略了“最初”这个限定词。

#### 11.2 ATAM

🔴 **ATAM = Architecture Tradeoff Analysis Method，架构权衡分析法。**

核心是：

> 多个质量属性之间的**权衡（Tradeoff）**。

使用🔴 **效用树 Utility Tree**对质量属性进行分类、细化和优先级排序，叶子节点通常是具体的质量属性场景。

| ATAM结果 | 最短判断 |
|---|---|
| 🔴风险 | 可能不达标 |
| 🔴非风险 | 能达标、无明显问题 |
| 🔴敏感点 | 改一点，某个质量属性变化很大 |
| 🔴权衡点 | 一个决策影响多个质量属性，需要取舍 |

敏感点 vs 权衡点：

> **敏感点强调一个质量属性对某决策很敏感。**  
> **权衡点强调同时影响多个质量属性，通常需要一利一弊地取舍。**

### 12. 软件产品线

🔴 软件产品线特点：

- 核心资产
- 产品稳定性
- 过程驱动
- 特定领域
- 技术支持
- 以架构为中心

核心思想不是“每个产品从零开发”，而是：

> **基于共同核心资产和共同架构，在特定领域形成一系列相关产品。**

## 七、一页速记

### 开发模型

- 需求不清、快速做样品、用户反馈 → 🔴原型模型
- 需求稳定、阶段顺序清晰 → 🔴瀑布模型
- 大型复杂、高风险、风险分析 → 🔴螺旋模型
- 开发与测试阶段对应 → 🔴V模型
- 需求分析 ↔ 🔴验收测试

### 软件测试

- 最小单元内部逻辑 → 单元测试
- 模块连接后的问题 → 集成测试
- 修改后验证旧功能 → 🔴回归测试
- 链接目标/孤立页面 → 链接测试
- 不看内部代码 → 黑盒
- 看路径/控制流 → 白盒
- 边界附近取值 → 边界值分析
- 输入分组取代表 → 等价类划分

### 架构风格

- 数据流：批处理、管道-过滤器
- 调用/返回：主程序/子程序、面向对象、分层
- 独立构件：进程通信、事件驱动
- 虚拟机：解释器、规则系统
- 以数据为中心：数据库、黑板、超文本

### MVC / MVP / MVVM

- MVC：Model 数据/业务；View 显示；🔴Controller 交互控制
- MVP：🔴Presenter
- MVVM：🔴ViewModel

### SOA / 微服务

- 提供者🔴发布
- 消费者🔴发现
- 找到以后🔴绑定
- 微服务：细粒度、HTTP/REST/JSON、独立部署
- SOA：ESB、WS/SOAP

### 云计算

- 🔴IaaS 给资源
- 🔴PaaS 给平台
- 🔴SaaS 给软件
- 用户访问层 = 怎么访问
- 应用层 = 直接用应用
- 平台层 = 构建/运行应用
- 资源层 = 底层资源
- 管理层 = 统一管理
- 边缘计算 = 🔴靠近数据源处理

### DSSA / ABSD

- DSSA：特定领域 + 一组应用 + 共性抽象
- 垂直域 = 专、深
- 水平域 = 广、跨行业
- ABSD：🔴分功能、选风格、用模板

### 质量属性

- 性能 = 快不快
- 可用性 = 坏了还能不能用
- 安全性 = 该不该让你访问
- 可修改性 = 好不好改
- 易用性 = 好不好用/学
- 可测试性 = Bug 好不好测出来

### 质量属性场景

> 🔴谁（刺激源） → 🔴发生什么（刺激） → 🔴当时什么状态（环境） → 🔴作用到哪里（制品） → 🔴系统做什么（响应） → 🔴做到什么程度（响应度量）

### 架构评估

- SAAM：🔴最初主要分析可修改性
- ATAM：🔴多个质量属性之间权衡
- 效用树：质量属性分类、细化、排序

## 八、复习节奏

| 时间 | 任务 | 目标 |
|---|---|---|
| 今天结束前 | 看关键词 + 13 道错题 | 能说出错误原因 |
| 明天 | 重做13道错题 + 20道云计算/质量属性专项题 | 错题正确率100% |
| 3天后 | 闭卷复述一页速记 + 混合题 | 根据题干快速定位概念 |
| 7天后 | 再测一次100题级综合练习 | 检验长期记忆 |

## 九、复习原则

每道错题不能只记答案字母，要强迫自己说明：

> **题干关键词 → 为什么锁定这个概念 → 其他三个选项为什么不对。**

这是首轮 100 题最值得长期保留的复习方式。
