# P2.4 MySQL aggregate monitoring candidate — offline only (#450)

Official mysqld_exporter v0.18.0, MySQL 8.4, P1 Prometheus v3.13.5 and Python 3.12 fixture, tags resolved to actual linux/amd64 image digests in disposable GitHub-hosted CI. No deployment, vulnerability clearance or live DB access. No PRP schema or records; only an empty synthetic denial-test table. No production credentials or account creation.

## Permission and target boundaries
The monitoring account is scoped to the exact exporter IP in the disposable DB network, USAGE only, maximum two concurrent connections. No SELECT, PROCESS, REPLICATION CLIENT, schema or write privileges. Test actual successful global status/variables collectors and forbidden reads/writes/process/privilege changes without granting more permissions. Explicitly turn off other default-enabled collectors: slave status, innodb_cmp/cmpmem, query_response_time. Do not collect processlist, statement digest, per-user/schema/table metrics or replication. The raw exporter is not a permission boundary; v0.18.0 accepts target overrides even at /metrics. A separate fixed-target proxy forwards only exact GET /metrics with no query to the configured exporter, never caller headers or redirects. Private DB network is separate from the scrape network; only the proxy bridges both, no host published ports, no Docker socket, no privileged mode. The proxy is a disposable proof, not a production gateway. Raw exporter global-variable output is internal; Prometheus retains only fixed aggregate metric families and labels. No real monitoring targets. Plain HTTP/isolated DB connection is not an approved production TLS solution.

## Acceptance
Compare configured maximum connections, uptime, command count and aggregate InnoDB metrics with fresh server status; confirm only intended collectors succeed, raw metadata/credential markers absent, TSDB series bounded. Verify synthetic table SELECT and mutations denied, exact account host and grant scope, connection limit, fixed-target HTTP denial, network isolation, DB-down vs scrape-path-down and fresh recovery. Report actual container resource snapshot, not peak or storage forecast. No query latency distribution, SQL text, real data or replication metrics. Dashboard JSON is a candidate and is not imported.
