# P2.2 application performance monitoring — offline only (#450)

Independent from #451 P1 running pilot and #463 P2.1. No production deployment, real monitoring target, new credentials, changes to existing SecurityConfig, OAuth, MCP, nginx, compose, release hold or shared CI. Dependencies use the existing Spring Boot 3.5.3 BOM; no independent metrics framework.

## Default and opt-in
Without the observability profile, management.server.port=-1, endpoint access max-permitted=none, web/JMX exposure excluded, Prometheus exporter disabled and metrics denied. Existing health routes remain unchanged. The candidate profile permits only Prometheus read-only, binds a separate IPv4 loopback listener (candidate 19091), requires a dedicated bcrypt cost 12–14 hash with no default password, uses an isolated in-memory provider and stateless HTTP Basic; the management role is not a PRP user or OAuth/MCP authority. Requests must be GET /actuator/prometheus on the actual management port from loopback. No environment, heap dump, config, beans, or management discovery exposure. No plaintext credential in the repo. Missing hash or unsafe configured address/port fails startup. The localhost-only HTTP Basic setup is a CI candidate, NOT a remote scraper or deployment recipe; a separate approved network/TLS/access review is required before any real integration. Prometheus container access is deliberately not configured.

## Metrics
JVM memory/GC/threads, process CPU/uptime, system CPU, application startup, HTTP server duration/count/status/method and templated URI, Hikari aggregate pool metrics. Standard Spring Boot observations only; filter denies other families and unapproved tag keys; caps distinct URI 256, method 16, pool 8, with bounded 100ms/500ms/1s/3s latency SLO buckets (not full percentile histogram). Cap may omit new series after exhaustion; no raw URL/query/header/body, owner or business ID tags. A future enabled profile needs real route cardinality and resource review, including JVM tag values and credential hash-check CPU. Do not treat Hikari connection health as business/database correctness.

## Evidence
Full existing CI plus dedicated GitHub-hosted disposable MySQL test. Actual application random HTTP ports with test in-memory profile verify management disabled, valid/wrong/missing credentials, no business access from metrics role, unrelated paths and methods denied, real JVM and HTTP metrics and raw-request marker exclusion. Direct Hikari/Micrometer tracker test uses a fresh synthetic MySQL pool and checks borrow/return gauges; it does not attest production datasource wiring or real target performance. Label caps tested in a fresh registry. No real server, database, credentials or data. Historical #403 application.yml file-level overlap noted; keep independent and reconcile only under future separate authorization. P1 stable observation and P2.1 remain unaffected.
