# Offline receipt append / CAS contract

Stacked review candidate depending on #422; review-only, no live writer. Proposed storage: receipts/<requirement>/<task>/<submit-request-id>.json on the protected prp-collab-state branch, separate from requirements JSON. Append-only, one new file per commit, no overwrites or deletes. This avoids silently changing task schema/status/version; branch SHA still advances and all state writers must CAS on the whole ref, not version alone. The current live writer only allows the requirement JSON path; a separate independently reviewed and approved privileged receipt operation would be required to add this path, never a generic write endpoint.

Capture only from trusted GitHub reads at exact current protected state; no caller-provided receipt or flags. Existing bytes must be read at that same ref. Identical semantic evidence replays without write; conflicting evidence for the same submit fails closed. Reruns or base changes require explicit rework/resubmit and new receipt; do not overwrite historical evidence. Before committing, re-fetch exact PR/checks/run/job evidence and compare against the planned bytes, including CI and base; validate one parent and single added path, then non-force push, independently read back exact SHA and content. If competing update wins, discard local plan, re-fetch and recapture; no force/retry of stale bytes. Capture and receipt commit must precede owner-authorized merge. A timestamp/digest alone is NOT protected-origin proof; future trusted accept must independently verify receipt commit lineage, writer identity, append-only path and exact parent state, and independently verify receipt was committed before merge. The workflow run's PR metadata can be mutable; durable capture must also bind the actually tested synthetic merge/tree to each required job, e.g. reviewed immutable attestation or trusted checkout evidence, not infer it from a current PR merge_commit_sha. No live collector, privileged workflow, or accept wiring here. Local bare Git CAS test uses synthetic fixtures in temporary directories and no remote services. Do not activate without separate security review; #415 historical recovery and #391 activation remain separate. No state change, production or Health changes.
