# Pre-merge provenance receipt contract (review only)

## Objective
GitHub can remove Actions run.pull_requests associations after a PR is merged (#415 observed). Record verified exact pre-merge associations BEFORE merge, and revalidate the persisted evidence after merge without accepting mutable comments, worker assertions or arbitrary logs.

## Contract
The pure review-receipt module requires the latest task ledger event to be submit, pins the claim fingerprint (including generation), submit request/version, PR and same-repository numeric identity, exact protected integration ref/base SHA, head, GitHub synthetic merge commit/tree, identical critical workflow blobs and all seven latest successful GitHub Actions check/run/job/attempt identities. Existing strict scope and provenance validation is retained. Post-merge verification compares both Git objects' ordered parents and tree, actual ancestor and protected branch, same active submitted lease, exact job identities and current green workflow results. Empty post-merge run associations are permitted only against this exact persisted pre-merge receipt; conflicting nonempty associations are rejected. Any later task-specific ledger event, rerun or retarget requires a new pre-merge receipt or explicit separate recovery review. Other tasks may advance the global version.

## Trust boundary and storage (not yet implemented)
1. Owner-authenticated protected-main workflow reads real GitHub state/ref, PR, merge candidate Git object, workflow file blobs, complete checks/runs/jobs. Validate exact repo/rulesets, publication hold and current claim. Capture before merge; persist immutable receipt in protected state using reviewed CAS (no worker-controlled receipt or trust flags). Receipt digest is an integrity checksum, NOT a signature or proof of protected origin. Store under requirement/task/submit request identity; reject duplicates with different digest; no claim UUID in receipt.
2. Re-read mutable evidence and current state immediately before committing receipt, protect against stale writes, then separately authorize merge with expected head and base; strict CI plus merge-commit-only rules. Refuse if tested tree or exact base changes.
3. After merge, retrieve receipt from the authoritative protected ledger and reverify current task and evidence, both Git objects, ancestry and workflow identity. Only a separately reviewed trusted accept runner can mutate state after another pre-push verification. No implicit DONE.
4. The present module is deliberately not wired to issue ingress, core state schema, coordinator or live workflows. The storage transaction and trusted collector still need separate review, owner authorization, local CAS integration tests and actual live acceptance. No generic history backfill. #415 predates this mechanism and requires independently authorized historical recovery (#419). #391 remains separate. Current main/dev/integration and production are not changed.

## Limitations
Strict one-page completeness bounds fail closed; fields such as run.pull_requests[].base.sha and repo.id must be available at capture, otherwise do not issue a receipt. The existing state ledger does not itself persist receipt bytes; callers must not treat this prototype's digest or return value as trusted authorization. GitHub APIs are not atomic; reviewed CAS and repeated remote reads are still required. No additional GitHub permissions requested by this candidate.
