This first P3.5 slice is an executable Java **test-source-only** prototype (not included in the backend JAR). No configuration, route, MCP scope registration, app UI registration, endpoint, application schema migration, release workflow, publication hold, deployment or server operation changes.

## Why another proof is required

Reuse the existing OAuth verified-principal capture and client/owner scope model: McpVerifiedPrincipalCaptureFilter, McpOAuthTransportConfiguration.VERIFIED_AUTH, McpScopeGuard.VerifiedClient, UserStore, McpClientGrantService. Current transport uses signature-validated OAuth, linked active PRP account, signed exact client identity and intersection of granted scopes. Current wellness app-only approval is not independent cryptographic human proof; do not copy its automatic confirm sequence or modify its code. App-only visibility is host-enforced, not independent identity evidence. Do not accept a model decision, an HTTP header, caller asserted user ID, app-only flag, ordinary JWT alone or a password in chat as production release authority.

## First isolated contract

Fixed environment prp-unified-396, fixed ChatGPT client ID, distinct proposed prp.release.staging.review scope (not registered/granted). The prototype accepts only server-captured authenticated UserProfile + VerifiedClient, exact configured owner, current enabled account and fresh owner grant, plus a separately server-captured verified session digest. Existing transport does not yet expose this session proof: tests install a synthetic typed request attribute; no live bridge exists. The pending context is obtained from a future trusted ledger/collector, never card/model arguments. It binds UUID, owner, session digest, commit, tar SHA256, schema, CI run/attempt, evidence digest and expiry. It must be refreshed and compared atomically in the future; the present prototype validates the supplied server-owned context, not GitHub or hold state.

The decision envelope includes approval ID, approve/reject enum, nonce, issue/expiry and Ed25519 signature. Domain-separated fixed-field canonical bytes bind the exact environment/client/scope and all pending fields + decision and nonce/time. The public key is pinned by the test harness, private key generated ephemerally in tests only. This verifies real cryptographic integrity in CI, **not** a genuine ChatGPT host human-click issuer. No evidence of such a production issuer is established; do not mint a signature merely because a tool request arrives. Proof max 60 seconds, pending max 15 minutes, server clock, strict expiry, no in-process replay or competing decision, bounded 128 records. Both approved and rejected results are REVIEW_RECORDED_ONLY and every authorization/live flag is false. No consume, promote, dispatch, Shell or external calls.

## P3.5.1 durable decision rehearsal

The verifier delegates its atomic receipt/nonce/clock boundary to a test-only DecisionJournal. The default bounded memory implementation remains for unit tests. A disposable MySQL adapter runs only when GITHUB_ACTIONS=true and the dedicated CI opt-in is set, using the existing fixed loopback MySQL service and synthetic CI credentials, with random scratch table suffixes, no app schema or migration. Each receipt and monotonic clock/count update share an InnoDB transaction and singleton row lock; unique approval ID and nonce protect across independently reopened connections. A receipt is returned only after commit. The DB stores only ID, nonce, enum, SHA256 of canonical proof bytes and record time. Six integration tests cover durable replay, competing decisions, nonce uniqueness, rollback on a failing metadata update, persistent clock and forged proof. The tables are created and removed by tests; no runtime registration, real staging database, schema migration, trusted host issuer, dispatch or production state. The adapter is not a proposed production ledger: pending record creation, authenticated source, expiry at DB transaction time, role mapping, retention, grant/candidate freshness in the same transaction and independently verifiable audit still require separate design and verification.

## P3.5 — locked decision freshness recheck

The boundary now requires a separate server-owned CurrentReview supplier on every invocation; no default stale snapshot fallback. CurrentReview (pending record and explicit PASS/BLOCKED/UNKNOWN fixture state) is test-only, not a trusted real collector. After the memory or InnoDB journal takes its exclusive decision lock, it reloads that source, requires exact pending equality and PASS, rechecks the captured identity/session and current account/grant, samples the clock again and validates proof/pending expiry and monotonicity before receipt insertion. Eight additional MySQL tests hold the singleton row lock on an independent connection, wait for the initial grant read, then advance clock or change grant/account/candidate/gates/session/source, release the lock and assert denial with zero receipts; unchanged control succeeds. The current source and grants are mocked and not locked in the same database transaction as the journal. This narrows the pre-lock stale-check window only; it is not atomic live evidence/permission freshness, durable pending-state storage, genuine host proof or dispatch authorization. No new CI job or runtime paths; existing disposable MySQL IT step executes the added cases.
