# Remote Executor V1.1 — detailed offline candidate

Status: P1 protocol and P2 offline ledger/spool candidate implemented; tests pending exact-head CI. Reuse #277 / #273 / #296 / #299 CMS and SSH transport; reference #309 / #424 security findings and #396 / #456 regression contract. No activation, new live permission, merge or deployment authorized.

## Objective and delivery scope

ChatGPT prepares a bounded job including command or file manifest, shows the proposed impact and obtains explicit approval for execution and mutations. The existing GitHub connector transmits the approved job; the server receives and verifies files, runs a sandboxed script or a fixed staging handler, and returns authenticated encrypted status/results. Daily operation requires no manual SSH, upload or GitHub UI after a separately authorized one-time installation. The existing production V1 remains disabled.

Historical workload classes: read-only diagnostics, small Python/Bash scripts, multi-file configuration validation, large CI image artifacts (~203 MiB), staging preflight and regression. Shared host root, Docker, ingress and production changes cannot be replaced by an unrestricted script runner.

## Architecture and transport

Separate staging-only protocol namespace, SSH identity, recipient certificate, result signing identity, ledger and environment. Reuse existing CMS, pinned host verification and safe diagnostic labels. Fixed owner-only issue_comment entry and trusted default-branch workflow, never pull_request code with live credentials. No new public HTTP listener or self-hosted GitHub runner on shared host. No production V1 gate modification. GitHub owner identity is not independent cryptographic proof of chat approval; document and accept residual risk explicitly before activation. Trust only verified owner-created events, bound to exact request, expiry and nonce.

Three file sources:
1. Bounded encrypted inline envelope for small scripts/configuration; conservative 8 KiB total file payload initially, subject to measured CMS/comment overhead. Multiple files with manifest; no plaintext on public GitHub. Chunking may be considered only after measured connector limits and quotas.
2. Immutable repository file at exact commit and path (non-sensitive source already in repository); verify SHA256 and size. Never resolve moving branch at execution.
3. Existing GitHub Actions artifact from a trusted producer, bound to repository, workflow, successful run ID, exact source SHA, artifact ID, name, size and SHA256. Download on trusted hosted runner and stream over the dedicated SSH channel into a staging spool. Verify outer archive and inner file manifest; no arbitrary URL or user-selected credential target. Initial proposed large transfer ceiling 512 MiB, only after disk/capacity tests and approval. Use resumable transfer by bounded verified chunks if necessary; no execution until all bytes verified. Never place binary images, confidential input or unencrypted logs in the public repository.

For arbitrary large local/chat attachments that are not already available from a trusted CI artifact, the existing connector exposes no verified general attachment upload API. Do not promise zero-click upload for these files. Design an optional private artifact provider/upload adapter only if needed, with separate authorization and connector capability verification; prefer rebuilding repository-derived artifacts in CI. Do not require manual upload for normal CI-generated artifacts. No arbitrary outbound URLs.

## Job contract and approval

Job UUID, protocol version, staging target, operation enum, task/issue reference, immutable file manifest (relative paths, bytes, SHA256, source IDs), entrypoint/interpreter, typed args, bounded limits, expiry, nonce and response certificate. Canonical manifest digest includes operation, target, artifact IDs/digests, arguments and limits; approval is for this exact digest and target. Any change needs renewed approval. Transfer-only is also a separately bounded action; scripts cannot be executed merely because upload succeeded. Distinguish fixed read-only operations (within explicit existing authorization), sandbox execution, and fixed staging mutations. No permission for arbitrary production or privileged shell, sudo or Docker socket. Existing test/business-write approvals still apply.

## Execution

Receive into per-job private spool, enforce disk quota and file count/size, reject traversal, absolute paths, symlinks, devices, duplicate paths and archive expansion bombs; write atomically and verify hashes before readiness. Never write to /root or live application paths. Script sandbox: separate non-root identity, no host/prod mounts or secrets, no Docker socket, no network by default, bounded CPU/memory/PIDs/time/output, whole scope descendant cleanup, no privilege escalation. Real boundary requires host verification; if isolation cannot be proven, run on separate disposable VM or hosted CI only.

Staging-specific operations use separate reviewed, fixed typed handlers or existing authorized runner interfaces. Initial handlers: staging health/preflight and artifact inspection; image import, stage restart or route updates remain disabled until an exact target, reviewed handler, backup/rollback and authorization are available. Shared Nginx changes are not general sandbox operations. Never pass caller scripts or arbitrary parameters to root/sudo/Docker. Reuse #396 runner and existing staging mutual exclusion; do not run business CRUD without its own approval. Stage-only mutations acquire existing shared lock and fail closed on contention.

## Status and results

Durable state machine RECEIVED -> TRANSFERRING -> VERIFIED -> QUEUED -> RUNNING -> SUCCEEDED/FAILED/TIMED_OUT/CANCELLED; separate REJECTED and UNKNOWN/RECONCILE_REQUIRED. Claim UUID/nonce transactionally before side effects. Resume transfer by manifest; never automatically replay uncertain execution. Read status without re-executing. Provide job ID, timestamps, digest, exit status, bounded sanitized stdout/stderr, result artifact manifest and authenticated receipt; encrypted payload to public issue only. Sign response with pinned server identity; bind receipt to job, manifest and request. Durable server result can be retrieved in a later authorized chat with a fresh response certificate; do not depend on a previous ephemeral private key. Status/results scoped to authorized owner/job, no public plaintext or secrets. Cancellation cooperative/whole scope, does not imply rollback.

## One-time installation and acceptance

Separate staging account/forced command/key/cert and root-owned configuration, dedicated nonprivileged spool and sandbox, trusted workflow default-branch activation and staging-only credentials; no general root/Docker privileges. Preserve revoke/disable switch and independent production hold. Install only after exact-head CI and independent review and separate approval; verify no prod routes, mounts, credentials or identity sharing. Proposed limits: one concurrent mutation; sandbox concurrency initially one; 8 KiB inline, 512 MiB large artifact, bounded 64 KiB result with measured encrypted transport chunks, per-job disk/TTL and timeout to be confirmed with capacity. No additional governance service, database or UI; local SQLite ledger and existing GitHub connector are sufficient.

E2E acceptance: harmless Bash/Python, multi-file upload with SHA256, trusted CI artifact >=203 MiB transfer and verification, staging read-only check, status from new chat, duplicate/expired/rejected/timeout and descendant cleanup, interrupted transfer recovery, no production access. Fixed staging mutation tested separately only with existing scope and approval. Negative cases: wrong actor, wrong target, tampered digest/signature, path traversal, unsafe archive, quota, arbitrary URL, unexpected source, lock contention, unauthorized status, production mount/network and credential leakage. CI green is not live validation.

## Implementation checkpoint P2

The internal Ledger provides durable SQLite job/nonce claim, private per-job files, bounded streaming with SHA256 verification, atomic file publication, preclaim re-verification, single active/uncertain job, pending cancellation, persistent status and bounded result. It has no network interface. Interrupted transfer restarts a single file from byte zero; true chunk resume remains P3. A default-disabled Bubblewrap launch adapter now exists, but no actual shell, Python, SSH, or staging operation has been exercised. The caller must authenticate, bind approval and provide a validated isolation adapter; the manifest digest is not an authentication credential. Remaining live blockers include cumulative disk quota/TTL/cleanup, trusted spool ownership and separate sandbox identity, transport deadlines, host resource isolation, result signing, stage mutex integration, and explicit uncertain-state reconciliation. Offline tests use temporary local storage and synthetic result records. No live server activation.

### P2 sandbox checkpoint

The adapter requires the fixed root-owned one-time sandbox gate, trusted immutable dedicated rootfs and launcher paths, non-root worker, no-new-privileges and bounded dedicated cgroup v2. It constructs an argv-only rootless Bubblewrap invocation with read-only input, isolated namespaces, no host mounts/network, minimal environment, bounded output and no host-shell fallback. Mocked launch tests validate argv, failure/timeout uncertainty and result persistence. Actual user namespace compatibility, rootfs provenance, whole-process cleanup and cgroup isolation are unverified; see install-review.md. Timeouts remain RECONCILE_REQUIRED until independently reconciled. No activation, installation or deployment.

### P3 artifact bridge checkpoint

The offline bridge checks exact owner-created GitHub issue-comment event context, separate V1.1 protocol, fixed repository and main ref. An injected trusted provider supplies run and artifact metadata and binary streams. Artifact source must match an explicitly allowed workflow filename and exact SHA, successful run, repository, artifact ID/name/size/expiry and API SHA256 digest. Missing metadata rejects; real GitHub API shape and digest availability still need live read-only verification. The ZIP is streamed into a private temporary file, its outer SHA256 and size checked before member inspection; reject unsafe paths, case duplicates, symlinks, encrypted or unsupported entries and oversized expansion. Selected members stream in 1 MiB chunks into the existing ledger and are independently hash checked. Inline and immutable repository inputs are supported. A 203 MiB synthetic local-file test is included, not a real GitHub/SSH transfer. No network adapter, SSH framing, CMS authentication, signed receipt, durable transfer resume, live workflow or server installation in this checkpoint. Never trust the declared source or comment as independent approval proof. Production remains disabled.

### P3.2 secure envelope and framing checkpoint

The V1.1 CMS implementation uses local OpenSSL and AES-256-GCM encryption, with strict bounded JSON, dedicated staging target, submit/status/result actions, request UUID/nonce, exact job and manifest binding, short-lived requests, and a caller-supplied reply certificate. Results are signed with a separately trusted server signer certificate and encrypted to the request-specific reply identity; verification uses the pinned signer, never embedded certificate trust. A new query can use a fresh reply identity without rerunning the task. Encryption by itself is not sender authentication, and the current decrypt primitive does not enforce an incoming CMS algorithm profile; trusted transport and independent approval remain mandatory. Query replay claims, server-side authentication of the actual event, result dispatch, production key separation and key provisioning are pending. The binary file frame contract carries canonical bounded header, job UUID, manifest digest, relative path, offset, SHA256 and final indicator; the receiver rejects corruption, sequence mismatch, truncation and trailing data, and the ledger independently verifies the full file. This is a local stream contract, not a live SSH channel or resumable transfer. Synthetic ephemeral OpenSSL identities and in-memory streams only. No server enablement, credentials, workflow activation or deployment.

### P3.3 GitHub provider and stream sender checkpoint

A read-only GitHubProvider candidate uses fixed repository API routes, TLS verification, no environment proxy inheritance, bounded metadata/stream reads, exact source SHA, and one HTTPS artifact redirect to an operator-pinned exact storage hostname. Authorization is never forwarded to storage; a second redirect is rejected. GitHub connector read-only evidence from Feature Impact run 45776290060 confirms artifact metadata includes digest, size_in_bytes, workflow_run.id and head_sha. No live download or token use was exercised by this candidate. Storage hostname and actual download compatibility must be confirmed by authorized read-only testing. Socket inactivity and checked stream deadlines are not a hard wall-clock bound under all network conditions; a supervised worker deadline remains required. The frame sender checks total source size/digest and emits bounded frames for the existing receiver. The SSH argv builder uses a fixed staging account and receive-v11 command, pinned known_hosts, no agent or forwarding, no arbitrary command, and ignores user SSH configuration. It does not launch SSH. Server forced-command receiver, authenticated request/identity dispatch, actual transfer supervision and durable query replay handling remain pending. All tests use mocked HTTPS, local streams or synthetic identities. No server activation, new live workflow, merge or deployment.

### P3.4 local dispatch checkpoint

The internal dispatch adapter validates the dedicated issue event and encrypted request, durably claims request UUID, nonce and comment ID, transfers and verifies submit files, and returns an encrypted server-signed receipt. Fresh status/result requests resolve the exact existing job and manifest hash and read a single SQLite snapshot without invoking transfer or execution. The dispatcher never launches scripts or mutates staging. Synthetic integration tests use temporary identities, a local spool and explicit synthetic worker completion; queries after reopening the ledger and with a fresh reply certificate must recover the same result. Invalid actor, wrong issue, wrong digest, repeated comment/nonce/request and replay after reopening reject. This is not an authenticated external endpoint: the caller still must establish trusted event provenance and explicit approval, and the SSH service must bind its verified transport identity. A claim committed before a transfer/signing failure is not automatically retried; safe recovery and retention/quota remain outstanding. No live GitHub comment posting, SSH process, workflow activation, stage mutation, installation or deployment.

### P3.5 duplex SSH relay checkpoint

The runner and receiver now have a bounded duplex session contract: runner forwards the authentic owner event via a dedicated pinned SSH connection; receiver alone decrypts the CMS request and claims the request/job; receiver returns a bounded external-file plan over the SSH channel; runner fetches approved immutable repository/CI artifacts, validates them and streams file frames; receiver independently verifies every file, completion marker and EOF before transitioning to VERIFIED and returning the signed encrypted receipt. Inline bytes remain on the receiver. No permanent GitHub download token on the server and no server CMS private key on the runner. Queries send an empty plan and never transfer/execute. Local socketpair tests cover repository/inline and CI artifact relay plus fresh-identity result retrieval. SSH process candidate uses fixed argv, private temporary credentials with final LF, monotonic pipe deadlines, bounded wait and process-group cleanup; provider calls still require an independent hard overall supervisor deadline. Default enabled=False; no actual SSH call tested. The eighth file is a manual blocked-only workflow, with no issue trigger, credentials or execution step. It is deliberately not an operational workflow. A separately authorized installed receiver, host-local gate, actual trusted event/transport identity binding, producer allowlist usability, result posting, worker scheduling, disk/retention safeguards, real sandbox and stage handlers remain necessary before activation. No production permission, deployment or merge.
